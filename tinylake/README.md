# TinyLake — 对象存储之上的轻量表格式层

用 Go 实现的迷你 Lakehouse 表格式（Iceberg/Delta 的核心语义简化版）。在对象存储的不可变文件之上，
用**元数据快照 + 指针 CAS** 管理表的文件清单，解决流式小文件、并发覆盖写、查询裁剪、安全清理等问题。
本地用目录模拟对象存储，无需任何外部依赖。

## 解决的问题

数据湖里 Parquet 小文件越堆越多、查询越来越慢，两个任务同时写还会互相覆盖。TinyLake 给出：

- 每次写入是一次**原子提交**，读者要么看到整批、要么看不到
- 多写入方**乐观锁并发**，冲突自动合并重试，互不覆盖
- 后台把小文件合并到目标大小，**合并期间读写不阻塞**
- 同一批数据**精确一次**（exactly-once），写入方崩溃重试不会写出两份
- 分区规格可演进（按天 → 按小时），**新旧分区共存且都能正确裁剪**
- 删除/更新先写**删除标记**，攒够后再物理重写
- 过期快照与孤儿文件**安全清理**，绝不误删正在被读的文件
- 统计每表文件数、平均大小、查询需扫描的文件数

### 关键设计

| 机制 | 实现 | 对应需求 |
|---|---|---|
| 原子提交 | 每次提交写一个**新的不可变元数据对象**，再用指针 CAS 切换；读者只跟指针走 | ① |
| 乐观锁并发 | 读当前指针 → 基于它构造下一版 → CAS，失败则重读 rebase + 指数退避重试 | ② |
| 唯一对象名 | 数据文件和元数据对象都用 `procID-时间戳-计数器` 命名，并发写永不撞键覆盖 | ② |
| 幂等去重 | 每次逻辑写有 `CommitID`（显式传入或由内容+writer+nonce 派生并缓存到请求对象），历史中已存在则返回 duplicate 空操作 | ④ |
| 后台合并 | 表级租约串行维护任务；先暂存合并产物，再以一次 `compact` 快照发布；与普通读写共享 CAS，不阻塞 | ③ |
| 分区演进 | 表里保留**所有历史分区规格**；裁剪只约束文件实际携带的列，新旧布局共存 | ⑤ |
| 删除标记 | `OpDelete` 只加 tombstone，读时过滤；`RewriteDeletes` 仅重写被污染的文件并回收失效标记 | ⑥ |
| 安全清理 | `BeginRead/BeginReadAt` 给在途快照加 pin；只删除既不被保留快照、也不被 pin 引用的文件；孤儿文件有 5s 宽限期 | ⑦ |
| 统计 | `Stats()`/`PlanScan()` 给文件数、平均大小、全表/分区/点查需扫描的文件数 | ⑧ |

> **踩到的两个真 bug（已修复并有测试守护）**
> 1. 元数据对象最初用「预测的下一个序号」命名，两个并发写入方会写同一个键，输家的 `Put`
>    在赢家 CAS 成功后覆盖其对象内容，导致赢家的文件从血缘中静默消失（提交成功却丢行）。
>    改为全局唯一对象名，顺序只存在内容里的 `Snapshot.Seq`。
> 2. 仅按内容哈希生成 CommitID，会让不同写入方的同构小文件碰撞成「重复提交」。改为混入
>    writer+nonce，并把派生 ID 缓存进请求对象，保证同一请求重试仍是同一个 ID。

## 快速开始

```bash
# 1. 跑端到端压测（默认 32 个并发写入方）
go run ./cmd/stress -root ./lake-stress

# 可调参数
go run ./cmd/stress -writers 40 -rounds 10 -rows 20 -target 1024

# 2. 启动管理控制台
go run ./cmd/tinylake -root ./lake-data -addr :8080
# 浏览器打开 http://localhost:8080
```

## 压测程序验证了什么

`cmd/stress` 分 9 个阶段，每个阶段后都做「期望行集合 == 实际可见行集合」的精确比对：

1. **32 个写入方并发提交**，随机注入 ~15% 崩溃重试（同一请求重发），验证乐观锁与幂等
2. **全量核对**：一行不丢、一行不重
3. **分区裁剪**（按天）：分区扫描文件数 ≪ 全表
4. **小文件合并**：对比合并前后扫描文件数，合并期间挂一个在途读者验证不被打断
5. **分区演进** dt → dt+hour：新老文件共存，天/小时两级裁剪都正确
6. **删除标记 → 物理重写**：标记读时即生效，重写后回收标记
7. **固定 CommitID 连提 3 次**：仅首次生效
8. **过期快照 + 孤儿文件清理**：植入孤儿文件、pin 住旧快照，验证不误删
9. 汇总统计

### 一次完整运行的结果（32 写入方 × 8 轮 × 20 行）

```
阶段1：256 次提交，36 次崩溃重试全部幂等命中，最大 CAS 重试 12 轮
阶段2：核对通过 5120 行，无丢失无重复
阶段3：全表 256 文件 → 限定单天只扫 39 个（跳过 217）
阶段4：合并 256 → 123 文件，扫描文件数减少 52.0%，数据不丢不重
阶段5：天/小时两级裁剪均正确
阶段6：25 个删除标记读时生效，物理重写移除 25 行、回收 25 标记
阶段7：同一 CommitID 3 次提交仅 1 次生效
阶段8：过期快照 263、数据文件 256、旧元数据 752、孤儿 26 全部安全回收
最终：期望 5235 行 == 实际 5235 行  🎉 8 项语义全部满足
```

## 与真实系统的边界

这是教学/原型级实现，数据行用 JSON 而非 Parquet，对象存储用本地目录模拟。
落地到生产时，`ObjectStorage` 接口可换成 S3/OSS（CAS 用 DynamoDB/条件写实现），
数据文件换成 Parquet，元数据快照模型与并发/清理语义可直接沿用。
